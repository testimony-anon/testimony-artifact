# Run notes: run roots, environment, time, usage, repairs

Companion to the paper's experimental sections. All numbers below are the ones reported in the paper; the underlying run manifests, provider envelopes and audit files are in this package.

## Environment
- Apple M5 Pro, 64 GB RAM, macOS 26.4; Python 3.12; headless Chrome 152 for recording.
- Conduit, Umami, Paperless-ngx and Ghost deployed with Docker; RWA run locally with Node.js 22. Every subject is reachable only on `127.0.0.1` and is reset from a frozen seed state before each validation run.
- Model calls with concurrency 48; network failures retried up to 3 times.
- Generation model for the reported results: DeepSeek V4.1-Flash (API model id `deepseek-flash`, OpenAI-compatible API), reasoning effort high, temperature 0.1, 3 independent generation rounds per input (union), one bounded completion call per uncovered write centre. The same settings are used by the ablation runs; only the evidence organization changes.

## Wall-clock time
- Main line (Full): Conduit 38 inputs about 1 h 45 min, RWA 45 inputs about 2 h 30 min for M1–M14 (subjects in parallel). Umami 22 inputs about 1 h 25 min including the resumes (its `m11fix-01` continuation took a further 11 min); Ghost 31 inputs about 1 h 55 min; Paperless-ngx M1–M10 in one pass plus about 30 min for the `m11fix-03` continuation of M11a–M14 (08:57–09:26 by the per-case log).
- Re-running M11–M14 on frozen candidates after the execution-framework fixes: 2–5 min per input.
- RQ2, Conduit and RWA: 77 faults x paired tests = 31,793 pairs, about 7 h on one machine. RQ2 on the other three subjects: Paperless-ngx 20 min for the whole pipeline, Umami 9 min, Ghost 33 min plus 76 min for the read/query faults.

The six ablation runs of the other three subjects ran in three phases between 06:44 and 14:48 of one day (phase 1 Umami + Ghost Temporal, phase 2 Umami + Ghost Flat and Paperless-ngx Temporal, phase 3 Paperless-ngx Flat), one application instance per subject at a time.

## Repairs to the execution framework during the study (all recorded in run manifests)

Conduit and RWA:
- The final test set comes from one generation; execution validation (M11–M14) was re-run on the frozen candidates after six execution-framework defects were fixed (prerequisite reconstruction, recorder body loss, member resolution domain, rebinding, protocol material shape, network retry). The fixes did not change the model inputs or the candidate sets.
- Temporal: RWA `L2-ONBOARD-02` failed on a malformed model reply (input-version field), one retry failed on a network outage, the second retry completed (`rwa/temporal-retry-02`, 23 retained tests, all structural constraints).
- Flat: RWA `L4-REQUEST-NOTIFY-01` and `L4-REQUEST-REJECT-01` failed on the same kind of malformed reply and completed after the retry logic was fixed (`rwa/flat-retry-01`, 257 and 263 retained); `L1-BANK-03` failed in relation closure on a projection path absent from the recorded observation and was continued from its frozen candidates after the fix (`rwa/flat-fix-01`, 44 retained: 41 structural, 3 business-level).
- Run-root precedence of the final RWA suite: `m11fix-02` > `rerecord-01` > `m11fix-01` (Conduit: `m11fix-01`). `rq1_extract.py` and `export_final.sh` take it from `DEEPSEEK_RUNS`; their built-in default was corrected to this precedence on 2026-09-20 (the earlier default `rerecord-01,m11fix-01` predates the `m11fix-02` continuation and reproduces only 2,113 of the 2,160 tests). The shipped audit files were produced with the corrected precedence (byte-identical re-extraction verified).
- Audit-file correction (2026-09-15): the tests of the two rerun cases above had no layer label in the first extraction (a stale export directory and a failed export); they were re-exported and re-extracted, the three new business-level tests were reviewed with the same procedure (all correct), and the affected counts were corrected (Temporal RWA structural 2,193 → 2,216; Flat RWA business-level 153 → 156, structural 3,351 → 3,392). The pre-correction files are kept under `snapshots/pre-layerfix-20260915/` in the two ablation audit directories.

Umami, Paperless-ngx and Ghost — four repairs to the run path, none of which touches the pipeline's decision logic:
1. **Deployment lifecycle.** The Umami data layer is a separate container that the run path does not start; it must be brought up once with `deploy/umami/db_up.sh` before the first supervised start (INSTALL.md). The Paperless-ngx materialize step was extended to run the migrations and the in-container seed in a throw-away `-prewarm` container, because the run path waits only for the HTTP readiness probe and then resets immediately, while the seed runs after readiness; without the prewarm the first reset finds no golden state.
2. **Reset subprocess and the virtual environment.** The run path spawns the subject's reset as `.venv/bin/python -m subject_adapters.docker_single_local reset` with a sanitised PATH and `PYTHONPATH`. On macOS that subprocess was observed not to recognise the virtual environment (`sys.prefix` was the framework Python's), so `import jsonschema` failed and every reset of the three subjects failed with `local_reset_failed:reset_subprocess`. The Conduit and RWA adapters need no third-party package and never showed this. The study's workaround was an untracked `sitecustomize.py` in the repository root that appends the virtual environment's `site-packages` to `sys.path` when the interpreter is not inside it; interpreters already inside the environment are unaffected. Reviewers who hit the same behaviour can use the copy that `scripts/experiments/rq2_subjects/rq2_subjects.py` writes into every fault root.
3. **Identifier disambiguation.** The binder assumed that identifiers observed in a recording are globally unique (slugs, UUIDs). Applications with integer primary keys make that ambiguous, so two disambiguation rules were added — take the shallowest `$.id` within one creation response, and disambiguate several creation requests by the path segments of the consuming requests — together with a runtime rule that an integer is compared as text once it is proved to be a string. The 9 frozen Conduit and RWA cases that were continued as a regression reproduced their M11b, M12 and M14 results item by item.
4. **Cookie sessions.** Replay of cookie-session applications needed the Django double-submit CSRF token (Paperless-ngx).

## Method changes tested but not part of the reported Ghost run

Two mechanisms were added to the implementation after the Ghost main-line run and are present in the shipped code: a profile field `read_semantic_endpoints` that declares request routes with read semantics (Ghost's admin interface issues `POST /ghost/api/admin/stats/posts-member-counts/`, a read expressed as a POST, inside the same operation window as a write, which made the anchor ambiguous), and a value-flow rule under which the path segments of a `Location` response header are no longer registered as an identifier source when the same scalar is already present in that response's body. The Ghost run reported in the paper predates both: its `environment.git_head` is `8000473a38`, and the profile it ran with declares no `read_semantic_endpoints`. No profile of any other subject declares such endpoints either, so the two mechanisms are inactive for every reported run. Note that the *shipped* fixture `fixtures/profiles/ghost_modular_local.json` is the current one and **does** declare the endpoint; the version the reported run used is shipped next to it as `fixtures/profiles/ghost_modular_local.paper-run.json`, and each case's own frozen copy is `…/union/inputs/subject/profile.json`. Use the `paper-run` file to re-run Ghost with the anchoring of the reported run. A rebuild of M1–M9 on the 83 frozen Conduit and RWA cases before and after the change produced byte-identical artifacts (14 kinds × 83 cases).

## Why primary-target coverage is not reported for three subjects

The paper reports primary-target coverage on the 71 Conduit and RWA sequences whose primary effect is API-observable. For Umami, Paperless-ngx and Ghost the per-sequence effect lists (`docs/design/cpv-expansion/rq1-audit-{umami,paperless,ghost}/scopes.jsonl`) were drafted after the runs rather than fixed at design time, and these inputs rarely read the written entity back by its identifier, so their correct business assertions mostly have a read as the producing request: of the sequences with a trace, 20 of 22 (Umami), 5 of the 7 that contain a write (Paperless-ngx) and 22 of the 26 that contain a write (Ghost) issue no by-identifier read of the written collection after the last write. `scripts/experiments/subjects/readback_after_write.py` recomputes these counts from the shipped traces. The coverage values computed from the drafted lists are in the `targets.jsonl` and `summary.md` of the three audit directories; the paper's Table III leaves the two coverage rows blank for these subjects.

## RQ2 on Umami, Paperless-ngx and Ghost: how the runs were executed

- The frozen Conduit/RWA evaluator (`ui_semantics.rq2_evaluation`) hard-codes their routes, catalogue and deployments and was left untouched. `scripts/experiments/rq2_subjects/rq2_subjects.py` reuses its projection (O0/O1/O2, business-only, unknown), its per-fault reduction and summary, its test-map builder and its HTTP seam, and adds a per-subject registry (`inputs/faults-<subject>.jsonl`, format in `inputs/FAULT-CATALOG-SPEC.md`) and a generic response-fault engine with shape-preserving operators that track the resources created, updated and deleted since the last reset (`rewrite_string`, `add_one_number`, `flip_boolean`, `old_value_after_update`, `omit_created_member`, `reinsert_deleted_member`, `stale_count`, and, for the read/query faults, `omit_first_member` and `drop_last_member` with an optional query-key gate).
- Source faults are executed from a *fault root*: a directory that mimics the package root by symlink and differs from it in one file, a copy of the subject's adapter whose `docker_single.volumes` block adds one read-only bind mount laying the patched file over its path inside the image. The image digest, the reset scripts and the recorded inputs are unchanged. `suite/FAULT-ROOTS.md` describes the mechanism; the fault roots themselves are rebuilt by `rq2_subjects.py prepare`.
- The runner waits for the subject's seed to finish before the first reset (the readiness probe passes earlier than the seed): Ghost's golden marker on the host, Paperless-ngx's `/usr/src/paperless/golden/.seeded` inside the container, Umami's `umami_golden` template database.
- Pairing, the O0/O1/O2 projection, the business-only condition and the unknown rule are those of Section IV-F. Response faults are paired with the qualified tests whose recorded normal reads match the fault's read routes; source faults are paired by the activating write route, as in the Conduit/RWA registry. A fault that no test pairs with stays in the denominator as *no test*.
- Qualification on the normal version: Umami 133 of 133, Paperless-ngx 738 of 738, Ghost 739 of 748.
- The Ghost registry was extended after registration: its qualified tests contain almost no writes, so five faults were designed from the read and query rules the recorded reads exercise; the six write-effect faults stay in the denominator. `docs/FAULT-CATALOGUE.md` section 5.4 states this.
