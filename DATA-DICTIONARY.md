# Data dictionary (where to look for what)

Every pipeline artifact is a JSON file validated against a schema in `contracts/` (the `schema_version` field names the schema). The most useful files per case run root `…/cases/<CASE>/union/`:

| File | Meaning |
|---|---|
| `run_manifest.json` | Configuration, code commit, model and parameters of the run; per-stage counts. `environment.git_head` is the commit the case ran on, `environment.evidence_organization` the configuration (`association` / `temporal` / `flat`). |
| `M01_09/proposal_evidence_view.json` | The associated evidence view shown to the model (after projection); `evidence_organization` marks the ablation configuration. |
| `M01_09/ui_api_trace.json` | The cross-layer trace: UI actions, request groups, anchors, and the `observation_ref` of each request into the recorded HAR. |
| `M01_09/rendered_candidate_input.json` | The rendered model input (summary stage batches and detail views). |
| `M10/union/candidate_set.json` | Admitted, deduplicated candidate oracles of the three generation rounds. |
| `../attempts/attempt-000N/M10/calls/<call>/` | One model call: `rendered_candidate_input.json` (prompt), `provider_response_envelope.json` (raw answer incl. usage), `candidate_validation_report.json` (admission decisions). |
| `M11a/material_set.json`, `M11b/` | Derived validation plans and execution materials (prerequisites, rebinding). |
| `M12/<candidate>/execution_evidence.json` | Executed requests/responses and the verdict (`validated` / `refuted` / `not-evaluable` / `infrastructure-failed`). |
| `M13/certified_relation_tests.json` | Compiled tests (blueprint + assertions). |
| `M14/final_calibrated_suite.json`, `M14/calibration_report.json` | Calibration in a fresh normal state; retained tests. |

Recording roots (`…/recordings-01/`, `deepseek-ablation-20260913/<subject>/recordings-final/`): `suite_manifest.json` (the inventory the recording was made from), `suite_recording_result.json` (per-case outcome and counts), `cases/<CASE>/actors/<actor>/<run>/session_bundle/` (the HAR and the session manifest the trace refers to).

RQ1 audit directories: `tests.jsonl` (one review packet per retained test: predicate, executed calls, evidence excerpts; the field `layer` separates the business-relation layer from the structural-constraint layer), `reviews.jsonl` (initial label C/E/U of the **business** relations, with rationale and model usage), `main-review.jsonl` (author adjudications of that layer: final label, rule A/B/C, `scenario_specific`, reason, evidence basis; see `docs/REVIEW-ADJUDICATIONS.md`), `tests-labeled.jsonl` (merged business labels; `label_source` says whether the final label comes from the initial review or the adjudication), `groups.jsonl` (semantic relation groups), `cases.jsonl` (per input case: run root, retained counts), `calibration.jsonl` (join with the previous round, where one exists), `targets.jsonl` (primary-effect checklist per sequence: `goals`, per-goal `coverage` full/partial/none with the covering tests, `has_correct_target`), `summary.md`. The free-text fields (reasons, goal texts, notes) were translated from the authors' Chinese working notes; labels and codes are unchanged. Audit directories that hold no `main-review.jsonl` had no instance to adjudicate.

Structural-constraint review — only in the four audit directories of the Full suites (`rq1-audit-deepseek` covers Conduit and RWA, `rq1-audit-{umami,paperless,ghost}` one subject each); the ablation suites were not reviewed at this layer:

| File | Meaning |
|---|---|
| `structural-reviews.jsonl` | One row per structural constraint (`layer == "basic_constraint"` in `tests.jsonl`), from the model-assisted initial review: `test_key`, `subject`, `case_id`, `candidate_id`, `predicate_family`, `label` (C/E/U), `reason`, `reviewer`, `prompt_version` (`structural-v1.0`), `prompt_sha256`, `response_sha256`, `usage`, `reviewed_at`. Same shape as `reviews.jsonl` plus `predicate_family`. |
| `structural-summary.md` | Generated per directory by `scripts/experiments/rq1_tools/rq1_review_structural.py --summarize`: the review object and criterion, the counts per subject, the breakdown by predicate family, the list of the items labelled incorrect with their reasons, and the token usage. |
| `structural-review-failures.jsonl` | One row per model call that returned no label (`test_key`, `error`, `failed_at`). Present only where such a call occurred. These items are neither correct nor incorrect; the authors decided them by hand. |
| `structural-main-review.jsonl` | Author adjudications of the structural layer: `test_key`, `label` (final), `class` (the group of the item, see `docs/REVIEW-ADJUDICATIONS.md`), `reason`, `basis` (source locations and evidence files), `reviewer`, `reviewed_at`. |
| `structural-labels-final.jsonl` | The final label of every structural constraint of that directory after adjudication: `test_key`, `subject`, `case_id`, `label`, `rule`, `reason`, `observation_call`, `predicate_family`, `initial_label`. This is the file the reported structural counts are computed from; the counts printed in `structural-summary.md` are the initial ones. `rule` records where the final label comes from: `structural_initial_review` (the initial label was kept), `classA_business_parity` (single-response constraints equating the number of members on the returned page with a count field of the same response, on a paginated endpoint, re-labelled by the authors so that this layer applies the same criterion as the business review), `group_amount_integer` (the RWA group asserting that every member's `amount` is an integer, made consistent after reading `backend/validators.ts`, which coerces `amount` with `toInt()`), `group_ui_settings_uniqueness` (the Paperless-ngx `dashboard_views_visible_ids` uniqueness group, made consistent) and `author_adjudication` (the one constraint the initial review never labelled). `docs/REVIEW-ADJUDICATIONS.md` gives the outcome of each rule. |

The review tool and its prompt are shipped as `scripts/experiments/rq1_tools/rq1_review_structural.py` and `scripts/experiments/rq1_tools/prompts/structural_review_v1.0.md`; the prompt's SHA-256 is recorded in every row of `structural-reviews.jsonl`, so the shipped text can be checked against the one the review actually used.

RQ2 of Conduit and RWA (`rq2-deepseek-final2-20260912/suite`, `rq2-20260907`): `response-faults.jsonl` (response faults: route, field, operator, trigger), `rq2-20260907/patches/*.patch` (source faults), `test-fault-map.jsonl` (fault ↔ test pairing), `outcomes-{normal,source,response}-<subject>.jsonl` (one row per fault–test pair with O0/O1/O2/B verdicts and assertion results; `evidence_ref` points into `suite/runs/`), `compositions.jsonl` (cross-flow compositions), `report.md` / `summary.json` (the Table IV numbers).

RQ2 of Umami, Paperless-ngx and Ghost (`rq2-subjects-20260921/`):

| File | Meaning |
|---|---|
| `inputs/FAULT-CATALOG-SPEC.md` | The registry format and the response-fault operators. |
| `inputs/faults-<subject>.jsonl` | One row per fault: `fault_id`, `kind` (`source` / `response`), `module`, `business_rule` and `description` (what is changed), `observable_effect`. Source rows add `routes` (the pairing routes, the first of which activates the fault), `affected_reads` (documentation) and `patch` (`container_path` inside the image, `patched_file`, `diff`, `original_sha256` of the image's file). Response rows add `reads`, `writes` (`method`, `path`, `role` create/update/delete, optional `id_path`), `operator`, `target` (the operator's parameters, e.g. `list_path`, `field`, `id_field`, `when_query_key`) and `substates`. `*.frozen-*.jsonl.bak` are the copies frozen before execution. |
| `inputs/test-map.jsonl` | Every retained test of the subject's final suite: `test_key`, `case_id`, `test_id`, `candidate_id`, `source_run`, `protocol` (validation plan), `layer` (`business_relation` / `basic_constraint`). Registered before any outcome was consulted. |
| `inputs/normal-<subject>.jsonl` | The normal-version run of every registered test: the qualification that decides which tests may pair with a fault. Same row shape as the outcome files. |
| `inputs/source-versions-<subject>.jsonl` | One row per source version (`normal` plus each source fault): the fault root, the container name, the image digest and the `docker run` argv, so that the read-only bind mount of the patched file can be checked. |
| `inputs/routes-<subject>.json` | The routes the recordings exercise, with counts, status codes, the cases they occur in and the response keys; the input from which the faults were designed. |
| `patches/<FAULT>/<file>` and `patches/<FAULT>.patch` | The patched copy of the image's file and its unified diff (exactly one hunk each). |
| `suite/outcomes-{normal,source,response}-<subject>.jsonl` | One row per fault–test pair: `fault_id`, `test_key`, `kind`, `layer`, `attempt`, `elapsed_seconds`, `evidence_ref` (into `suite/runs/`), the four verdicts `O0`/`O1`/`O2`/`B` (`detected` / `completed_not_detected` / `no_eligible_tests` / `unknown`), `business_direct_alarm`, `common_observation`, `mechanical_complete`, `application_5xx`, `error`, and `assertion_results` (per assertion: id, class, source, predicate type, definition digest, outcome). |
| `suite/response-faults.jsonl`, `suite/test-fault-map.jsonl`, `suite/selection-<subject>.json` | The registered response faults, the fault ↔ test pairing with the matched normal reads (`matched_request_refs`), and the selection record of the registration step. |
| `suite/report-<subject>.md`, `suite/summary-<subject>.json` | The per-subject result table in the layout of Table IV, and its machine-readable form with per-fault `paired_tests`, `substates` (activated responses per substate) and the tests that were structurally impossible to pair. |
| `suite/runs/<subject>/<kind>/<fault>/<CASE>/<test>/attempt-00N/` | The execution evidence of one pair: `http.jsonl` (every request and response) and `result.json`. The normal-version run is shipped in full; for the fault versions the evidence of the pairs that alarmed or stayed unknown is shipped. |
| `suite/FAULT-ROOTS.md` | Why `suite/fault-roots/` and `suite/runtime/` are not shipped and how `rq2_subjects.py prepare` rebuilds them. |
| `run_rq2_subjects.sh`, `rq2_driver.sh`, `rq2_ghost_extension.sh`, `ACTIVE-rq2-subjects*.json` | The launchers of the phases (`prepare`, `normal`, `register`, `responses`, `sources`, `summarize`) and the run-lock snapshots of the study's runs. |

RQ3: `rq3-<config>-comparison.json` (per subject and configuration: `funnel` (cases, admitted candidates `exact`, `ineligible`, the four M12 verdict counts), `usage` (prompt/completion tokens), `agg` (`retained`, `business`, `basic`, `C`, `E`, `C_groups`, `target`), `cases_with_C`, and `paired_on_correct_business_instances` with `improve`/`degrade`/`same`), the rendered tables `rq3-<config>-comparison.md`, and, for Conduit and RWA only, `evidence-dependence-<config>.jsonl` (one row per retained test: which evidence kinds the candidate cited).
