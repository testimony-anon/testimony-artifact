# Testimony — reproduction package

This package accompanies the paper *Testimony: Deriving and Validating Business-Level API Test Oracles from Web UI Execution Evidence*. Testimony is the paper's name for the approach; the implementation keeps its internal name — Python package `ui_semantics`, command `scripts/uisemtest`, environment variables `UISEMTEST_*`, and the names inside generated artifacts. The package contains the implementation, the 171 UI action sequences of the five subject applications and their recordings, every model input and raw answer of the reported runs, the validation evidence of every candidate oracle, the final API regression tests, the semantic-review records (RQ1), the fault catalogue with per-fault outcomes and defect reproduction scripts (RQ2), and the ablation runs (RQ3). All numbers in the paper can be regenerated from the files here.

## Three levels of reproduction

1. **Recompute every table from the included data (no network, no subject deployment).** See *Regenerating the paper's tables* below.
2. **Re-run validation and the final tests against the deployed subjects (no model key).** Deploy the subject (INSTALL.md), then run the exported pytest suites or continue a frozen run from its model output (M10) through validation, compilation and calibration (M11–M14).
3. **Full pipeline including model calls.** Requires a DeepSeek API key; model answers are not bit-reproducible.

## Running the final tests (level 2)

Each exported case directory (`…/<subject>/pytest-export-final/<CASE>/`) is a self-describing pytest module: `conftest.py` opens the frozen run root, and `test_final_calibrated_suite.py` lists every request, capture, binding and assertion. With the subject deployed and the test-account variables exported: `.venv/bin/pytest eval/ui_semantics/deepseek-full-20260912/conduit/pytest-export-final/L1-ARTICLE-01` or `.venv/bin/pytest eval/ui_semantics/ghost-20260921/ghost/pytest-export-final/L1-POST-01`. The runtime library (`ui_semantics.pytest_export`) resets the subject, authenticates the actors and injects fresh identifiers.

## Continuing a frozen run (level 2) and full runs (level 3)

`scripts/continue_frozen_case.sh <subject> <CASE>` re-executes M11–M14 for one Conduit or RWA case from its frozen candidate oracles (it wraps `scripts/uisemtest run --frozen-m10-source <case>/union --frozen-m10-completion-sha256 <sha> …` and picks the profile the case was recorded with); `scripts/experiments/rq1_tools/continue_frozen_m10_subject.sh <subject> <runs-root> <source-run> <new-run> <CASE>…` does the same for Umami, Paperless-ngx and Ghost. Live runs are gated by `docs/ACTIVE-EXECUTION.json` (a run lock used during the study); `docs/active-templates/` contains ready-made lock files for the documented commands of all five subjects. Full runs additionally take `--provider openai_compatible --provider-policy fixtures/provider_configs/deepseek_flash_current.json` with `DEEPSEEK_API_KEY` in the environment.

## Notes

- Absolute machine paths inside manifests were rewritten to `<ARTIFACT_ROOT>` (this directory), `<SUBJECTS>` (checkout directory of the subjects), `<PAPER_CODE_WORKTREE>` (the checkout of the pinned code an ablation was run from) and `<HOME>` during packaging; the recorded traces and model answers are otherwise unmodified. `scripts/relocate.py` fills the placeholders in on your machine (`<PAPER_CODE_WORKTREE>` only when you pass `--paper-code-worktree <dir>`; pass this directory to run the ablation launchers against the shipped code), except in three kinds of provenance manifests (recording session manifests, recording input manifests, recording workflow results) whose bytes are pinned by SHA-256 in the frozen lineage: those keep the placeholders, and `docs/artifact-relocation.json` maps their shipped digests to the original ones so that every pin check still passes (`ui_semantics/artifact_relocation.py`). `BUILD-REPORT.json` lists what the packaging step did.
- Test-account credentials in the fixtures and in `.env.example` are local placeholders, not real secrets.
- The implementation's earlier internal name, `carverflow`, survives in a few machine identifiers because the frozen artifacts carry them: the `tool_version` string of artifact envelopes (`carverflow 0.1.0`), the `x-carverflow-*` OpenAPI extension keys, the HAR creator name of the recorder, and the local placeholder accounts (`carver@carverflow.local`). It is not the name of a public project.
- The `contract_inventory` and `method_hashes` sections of the run manifests record the SHA-256 digests of the schema and source files at the time of each run. The shipped code is the state after the execution-framework fixes described in `docs/RUN-NOTES.md`, and its comments, docstrings and schema descriptions were translated into English for the package, so the digests of the shipped files differ from the recorded ones; the frozen-lineage pins that the pipeline verifies (recording bundles, input manifests, candidate oracles, model responses) are unaffected.
- The earlier round of the study with another model (gpt-6-astra, single round; the *previous round* of Sections IV-C and V-B) is represented only by its review scope list and export catalogues (needed by the summariser); its run outputs are not part of this package.
